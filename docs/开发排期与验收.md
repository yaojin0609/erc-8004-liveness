# 开发排期与验收标准（业余时间版）

> 配套 [实施规划.md](实施规划.md)（行为规格）、[接口契约.md](接口契约.md)（CLI/库/格式）、[schema.sql](schema.sql)（建表）。
> 每个 ticket 都有可机器验证的 DoD（Definition of Done）。**DoD 没过不许进下一个 ticket。**

---

## 1. 排期前提：业余时间怎么排

原始设定是「两周」。按业余时间算，两周约等于 **工作日晚 2h × 10 + 周末 6h × 2 ≈ 44 小时有效注意力**。整个排期按这个预算做，不按自然日排。

### 一个对你有利的结构性事实

本项目的耗时分成性质完全不同的两类：

| 类型 | 内容 | 耗的是什么 |
|---|---|---|
| **有人值守** | 写解码器、写探测引擎、做分析、写报告 | **你的注意力**（稀缺） |
| **无人值守** | URI 抓取（3–20h）、探测 R1（~3.3h）、探测 R2（~3.3h） | **墙钟**（廉价） |

**这三个长任务全部设计成夜里挂着跑。** 它们看起来是排期里最吓人的部分，实际上一分钟注意力都不占。业余时间做这个项目，反而比全职做更少浪费——你睡觉的时候它在跑。

排期的真正约束只有一条：**别让无人值守任务卡在关键路径上等你**。所以 URI 抓取必须在你写完抓取器的当晚就启动，不能等。

### 中断韧性（§0 C1）

这是可行性前提，不是工程洁癖。三条硬要求：

1. **每个 stage 幂等 + 可断点续跑**，写完一个就实测一次「杀进程再重启」。
2. **`e8004 status` 一条命令**回答：每条链每个 stage 跑到哪、哪些 DoD 已通过、下一步该干什么。**两周后回来的你会感谢这个命令。**（这是 T0 的 DoD，不是可选功能）
3. **每个 ticket 结束时数据库处于自洽状态**，随时可以停两周再回来。

## 2. 工作量与优先级（含诚实的总账）

**先说结论：44 小时做不完全部 14 个 ticket。** 下面是按优先级排的实话。

| 优先级 | Tickets | 预估 | 说明 |
|---|---|---|---|
| **P0 必做** | T0, T1, T3, T4, T5, T6, T8, T8b, T11, T12, T13 | **≈ 44.5h** | 产出完整的 L0–L3 漏斗 + 失败分类学 + 队列分析 + 开源仓库。**这已经是全部原创性所在**（实施规划 §2） |
| P1 强烈建议 | T2（Tier B 普查）, T7（反馈解码）, T7b（支付凭证） | ≈ 10h | T7b 只要 2h 但战略价值最高（§0 C3） |
| P2 可砍 | T9（资金溯源）, T10（经济活动） | ≈ 8h | 第一个被砍。L4/L5 层缺失，报告里如实说明 |

**P0 已经吃满并略微超出两周预算。** 所以现实的期待是：两周交付 P0，P1 必然溢到第三周，P2 看情况。别自欺。

如果你希望两周内连 P1 一起做完，只有一个办法：**把 T5（探测引擎，8h，最大的一块）的 dry-run 验证做扎实，别在 T6 之后回头返工。** 这个模块返工一次就是 P1 的全部预算。

### 砍东西的顺序（排期告急时按此执行）

1. 砍 T9/T10 → 报告没有 L5，如实标注
2. 砍 T2 → 只报 Tier A 三条链，口径说明写清楚
3. 砍 T7 → 报告没有 L4，但 L0–L3 完整
4. **绝不砍：T5 的验证、T6 的第二轮探测、T8 的交叉验证。** 这三个分别对应「不伤害别人」「结论可信」「数字正确」——砍掉任何一个，整份报告作废

## 3. 硬约束与关键路径

```
T0 脚手架 → T1 日志扫描 →[当晚启动]→ T3 URI 抓取 → T4 card 解析 → T5 探测引擎 →[夜间]→ T6 探测 R1
                  │                                                                        │
                  └→ T7 反馈解码 →[夜间]→ T7b 支付凭证                                 [≥48h]
                  └→ T8 交叉验证（正确性门槛）                                              │
                                                          T8b 探测 R2 ←────────────────────┘
                                                              ↓
                                          T9/T10（可选）→ T11 漏斗 → T12 报告 → T13 开源
```

三条不可违反的约束：

1. **探测两轮必须间隔 ≥48 小时。** R1 最晚要在你计划收尾前 3 天跑掉。业余时间排期下这条最容易被忘——**R1 跑在第一个周末的晚上是最安全的选择**。
2. **T3（URI 抓取）必须在写完当晚启动。** IPFS 可能跑 20 小时，卡在这里等就是浪费一整个工作日。
3. **T8 交叉验证不过就不许往下走。** 见 T8。

## 4. D0 —— 账号与资源准备（今天就做，不占开发预算）

这四样没有，T0 就会卡住。**在写第一行代码之前解决掉。**

| 项 | 说明 |

## T0 — 脚手架、地址与 ABI 验证、status 命令（P0，约 5h）

**目标**：把「扫错合约 / 解错 ABI」这个能毁掉整个项目的风险在第一天消灭掉；同时把中断韧性的基础设施建好。

**实现要点**
- `uv init`，装 `httpx eth-abi eth-utils duckdb polars typer structlog aiodns tenacity`。配置骨架已在 `config/` 下备好（`chains.toml` / `scan.toml` / `abis.json` / `blocklist.txt`），直接用。
- `abi.py`：读 `config/abis.json`，事件签名字符串 → `topic0 = keccak(signature)`。**运行时计算，禁止硬编码 hash**。
- `spool.py` + `db.load_spool()`：先建好落盘缓冲和入库通路（实施规划 §4）。**这个不先做，T1 就得返工。**
- `s01_bootstrap.py`：① `eth_getCode` 判存在；② IdentityRegistry 调 `supportsInterface(0x80ac58cd)` 应为 true，Reputation/Validation 调 `getIdentityRegistry()` 应等于 IdentityRegistry 地址；③ 部署区块二分查找（约 25 次 RPC），回写 `config/chains.toml`。
- **`e8004 status`**：输出格式见 接口契约.md §2。

**T0-1 子任务：核对 ABI**。`config/abis.json` 来自 EIP 规范正文，**规范与实际部署的合约可能有出入**。从官方仓库 `erc-8004-contracts` 的 `abis/` 目录拉实际 ABI，与本地逐个事件比对参数顺序和 indexed 标记。不一致以实际部署为准并更新 `abis.json`。**不做这一步，可能整个扫描解出来的都是垃圾。**

**T0-2 子任务：找 ValidationRegistry 地址**。官方 README 表格里没有。按序试：读仓库 `abis/` 与 `ignition/modules/` 部署产物 → 区块浏览器搜 `0x8004` 前缀合约 → 都找不到就保持空字符串并全流程跳过。**限时 1 小时，超时就降级，不许阻塞主线。**

**DoD**
- [ ] `e8004 bootstrap` 对 Tier A 三条链全部返回 verified，`chain.verified_at` 非空。
- [ ] `getIdentityRegistry()` 的返回值与配置里的 IdentityRegistry 地址**逐字节相等**（不等就是地址搞错了，停下来查）。
- [ ] 部署区块用 `eth_getCode(addr, deploy_block)` 非空、`eth_getCode(addr, deploy_block - 1)` 为空双向验证通过。
- [ ] **`config/abis.json` 已与官方仓库 `abis/` 逐事件比对过**，差异已修正或已确认无差异。
- [ ] **`e8004 status` 在空库、半满库、spool 未入库三种状态下都能正确打印下一步**，且「下一步」是可直接复制执行的命令。
- [ ] `e8004 load` 通路跑通：手工造一个 10 行的 JSONL，入库两次，表里仍是 10 行（幂等性实测）。
- [ ] ValidationRegistry 要么验证通过，要么配置里显式为空且有注释说明查过了。

## T1 — 日志扫描 Tier A（P0，约 6h）

**目标**：拿到 Ethereum / Base / BSC 的全量事件。这是权威数据源。

**实现要点**
- **写 spool JSONL，不直接写 DB**（实施规划 §4），扫完跑 `e8004 load scan-logs`。
- 一次 `eth_getLogs` 传地址数组，别一个合约扫一遍。
- 自适应步长：初值 10k；错误含 `range`/`limit`/`too many`/`-32005` → 减半；连续 5 次成功 → ×1.5。收敛值写回 `chain.max_log_range`。
- 上界用 `finalized` 标签；不支持的链退化为 `latest - confirmations`。
- 每条日志存 `block_hash`；续跑时先校验游标前 N 个区块 hash 仍匹配，不匹配则回退重扫。
- **解码陷阱**：`string indexed` 在 topic 里是 keccak 哈希。`tag1` / `metadataKey` 的可读值一律取 data 段的非 indexed 字段。

**DoD**
- [ ] `SELECT count(*) FROM ev_registered WHERE chain_id=1` 与 `8004scan.io` / Dune `hashed_official/erc8004` 的以太坊计数**同数量级且差异 <5%**。差异大必须解释清楚（很可能是口径不同——把解释写进 README）。
- [ ] 随机抽 20 条 `ev_registered`，用区块浏览器逐条人工核对 `agent_id` / `owner` / `agent_uri` 三个字段完全一致。
- [ ] 杀掉进程再重启，能从断点继续，`log_raw` 无重复行（实测一次）。
- [ ] 单元测试：至少 4 个**真实链上 payload** 的解码 fixture（用 `e8004 dump-fixtures` 取，见 接口契约.md §6），覆盖 `Registered` / `NewFeedback` / `MetadataSet` / `Transfer`。其中 `NewFeedback` 必须包含**负值 value**、**非零 valueDecimals**、**非空 tag1**（后者验证 `string indexed` 取的是 data 段而不是 topic 哈希）。

## T3 — URI 抓取（P0，写 3h + 无人值守通宵）

**目标**：把所有 `agentURI` 的原始响应落盘。**唯一网络出口 A。写完当晚必须启动。**

**实现要点**
- **先 `SELECT DISTINCT uri`**，先把去重系数打印出来看一眼——它决定这一步是 3 小时还是 20 小时。
- `data:` URI 进程内解析，零网络。**先跑完这部分，立刻有产出**（很可能占比不小）。
- IPFS：`local Kubo → w3s.link → ipfs.io → dweb.link → cloudflare-ipfs`，每网关独立令牌桶，单次 10s，最多试 3 个。CID 提取要支持 `ipfs://<cid>` 和 `ipfs://<cid>/path.json` 两种形态。
- HTTP：10s 超时、≤3 次重定向、**响应体上限 1 MiB**、记录 final URL。
- 内容寻址落盘 `data/raw/<sha[:2]>/<sha>`，同内容不重复存。
- 失败按 13 类分类（见 schema.sql 注释）。

**DoD**
- [ ] `uri_fetch` 覆盖 100% 的 distinct URI，无 `status IS NULL`。
- [ ] 每一类 status 至少人工抽查 3 条，确认分类正确（尤其 `not_json` 与 `http_404` 不能混）。
- [ ] 重跑一次，`attempt_count` 不增长、不产生新网络请求（幂等性实测）。
- [ ] 产出**第一个杀手级数字：元数据可解析率**，按 scheme 分组。原稿问的「30% 还是 3%」，这里出答案。

## T4 — Card 解析（P0，约 4h）

**目标**：blob → card / service / registration 三张表。纯函数，随时可重跑。

**实现要点**
- 严格校验 registration-v1：`type` 必须是 `https://eips.ethereum.org/EIPS/eip-8004#registration-v1`。
- 同时记 `parsed_lenient` 与 `schema_valid_strict`。
- `service.is_routable`：解析 endpoint host，判定 localhost / RFC1918 / 保留域名 / IP 字面量 → `FALSE`。
- `card_registration`：解析 CAIP-2 格式 `eip155:<chainId>:<address>`。

**DoD**
- [ ] `schema_valid_strict` 与 `parsed_lenient` 两个比率都算出来，差值有合理解释。
- [ ] `service` 表的 `service_name` 分布打印出来（web/A2A/MCP/... 各多少）。
- [ ] `is_routable = FALSE` 的样本人工看 10 条——**这批里大概率藏着报告最好的一个发现**。
- [ ] 单元测试：3 个畸形 card（缺 type / services 不是数组 / endpoint 是 localhost）走到正确的分类桶。

## T5 — 探测引擎 + dry run（P0，约 8h —— 最大的一块，最需要小心）

**目标**：写完 `probe/` 和 `limiter.py`，并**实测**限速真的生效。

⚠️ **这个模块返工一次就是 P1 的全部预算。** 宁可在这里多花 2 小时验证，也不要在 T6 之后回头改。

**实现要点**
- `DualLimiter`：全局 10 req/s + **per-host 1 req/3s + 同 host 最多 1 并发**，再加一层 **per-IP** 限速（很多 agent 端点是同一台机器的不同子域，只按 FQDN 限速等于没限——本项目预期正是这个场景）。
- 并发模型：按 host 分桶，起 200 个 host worker，每个 worker 串行处理自己 host 的目标。**不这么做的话 per-host 限速会把全局吞吐压成个位数。**
- UA：`ERC8004-Research-Scanner/1.0 (+<仓库URL>; <邮箱>)`。
- 只读：GET / OPTIONS / MCP `initialize` / `tools/list`。`tools/list` 由配置开关控制，想保守就关掉。
- 429/503 → 指数退避；同 host 累计 3 次 → 拉黑，记 `rate_limited` 而非 fail。
- 每端点每轮**最多 2 次尝试**。`config/blocklist.txt` 每次请求前检查。
- **库边界（实施规划 §11）**：`e8004.probe` 不许 import DuckDB、不许依赖本仓表结构。输入 endpoint 列表，输出带 `schema_version` 的结构化结果。**这条边界破了，三个月后第二阶段就是重写而不是扩展。**

**DoD**（伦理红线的代码化，逐条实测）
- [ ] `--dry-run` 打印将发起的请求总数与预计耗时。**全量探测前必须先跑一次核对量级。**
- [ ] 本地测试服务器记录到达时间戳：500 个请求打同一 host，实测**最小间隔 ≥3s**、**最大并发 =1**。
- [ ] 200 个不同 host 并发时，实测**全局速率 ≤10 req/s**。
- [ ] 日志确认每个请求都带正确 UA。
- [ ] 测试服务器返回 429 时，客户端确实退避且第 3 次后拉黑。
- [ ] 500 个真实端点抽样试跑，五层结果人工过一遍。
- [ ] **`python -c "import e8004.probe"` 在没有 duckdb 的干净环境里能成功**（库边界验证）。

**DoD**

- [ ] 复现论文的反馈集中度：ETH 前 10k 子集上，单一最大 client 的贡献占比应接近 **65.82%**。

## T7b — 反馈文件与支付凭证（P1，约 2h + 无人值守）

**性价比最高的一个 ticket**：完全复用 T3 的抓取器和限速器，只换 URI 来源和解析器，但产出的是你下一个产品的市场测量（实施规划 §0 C3、§5 Stage 07b）。

**实现要点**
- 先 `SELECT DISTINCT feedback_uri WHERE feedback_uri <> ''`，看量级再决定要不要抽样。
- 解析 `proofOfPayment`，然后**拿 txHash 去链上核验**（`eth_getTransactionByHash`，可批量，便宜）：交易真的存在吗？收付方真的匹配吗？
- 交叉检查链下 `value` 与链上事件 `value` 是否一致。

**DoD**
- [ ] 三个数字都出来了：`proofOfPayment` 存在率、**链上可核验率**、链下/链上 value 一致率。
- [ ] 「声称付过钱」与「真的付过钱」的差额被明确量化。**这个差额就是你后续那个产品要解决的问题的定量证明。**

## T8 — 集中度分析与流水线交叉验证（P0，约 4h）

## 贯穿全程的工程纪律

1. **网络 stage 与判定 stage 严格分离。** 判定逻辑会改二十次，探测只能跑两次。
2. **每个 stage 幂等 + 可断点续跑**，写完一个就实测一次「杀进程再重启」。
3. **解码器必须有 fixture 单元测试**，用真实链上 payload，别用手编的。
4. **金额与评分全链路禁止 float。**
5. 每天结束时备份数据库（`cp e8004.duckdb e8004.$(date +%m%d).bak`）。重扫一次的代价是几小时。
6. **T8 的交叉验证不过就不许往下走。**
7. **每次坐下来先跑 `e8004 status`，每次离开前确认数据库自洽。** 这是业余时间做长项目唯一可靠的方式。
