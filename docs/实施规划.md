## 0. 项目定位（决定了下面所有取舍）

这不是一个独立的数据分析项目。它是一个更长期押注的**起手式**，约束条件是：**业余时间、时间碎片化、无行业人脉、产出必须是可复利的积累型资产**。

由此产生四条贯穿全文的设计约束，与「纯粹做一份报告」的做法有实质区别：

| # | 约束 | 对实现的影响 |
|---|---|---|
| C1 | **中断两周不能死** | 每个 stage 幂等 + 可断点续跑不是工程洁癖，是可行性前提。必须有 `e8004 status` 一条命令回答「上次跑到哪、下一步干嘛」 |
| C2 | **墙钟时间廉价，注意力时间昂贵** | 长耗时任务（URI 抓取、活性探测）全部设计成**无人值守夜间跑**。它们吃墙钟不吃你的时间，反而是业余时间的朋友。真正稀缺的是写解码器和做分析的那几十个小时 |
| C3 | **报告会过期，scanner 不会** | 真正的交付物是那个可复跑的验证器。所以 `e8004.probe` 必须是能被别人 `pip install` 单独使用的库，输出 schema 要稳定。见 §11 |
| C4 | **这是押注，需要止损条件** | 报告必须能回答「值不值得继续投入一年」。什么数据算「值得继续」必须**开工前就定死**，否则事后一定会自我说服。见 §12 |

C3 带来一个具体的新增需求：**Stage 09（反馈文件抓取）**。规范里链下反馈文件带 `proofOfPayment` 字段——「我确实付过钱给它、它确实交付了」这条链路。有多少反馈真的带支付凭证，既是报告里的一个杀手数字，又直接给后续要做的「支付凭证 × 声誉绑定」做了市场测量。见 §5 Stage 07b。

## 0.5 实测修正（2026-08-10，写代码跑出来的，优先级高于本文其它任何论述）

以下四条来自实际跑链，推翻或改写了本文原先的判断。**实现时以这一节为准。**

### (1) 存在两组平行的注册表部署，不是「主网/测试网」

`e8004 diagnose` 实测：`0x8004a169`（A 组）与 `0x8004a818`（B 组）**都**部署在以太坊主网，
**都**是 ERC-721 `AgentIdentity`，连 implementation 都是同一个 `0x7274e874`。
区别在于近 10 万区块的 Registered 数：A 组 104 次，**B 组 0 次**。BSC 上 B 组更是完全
不同的合约（impl `0xd53de688`，非 ERC-721）。

→ 规范部署是 A 组。§1.1 里「一组主网一组测试网」的说法是错的，已在
`config/chains.toml` 更正。B 组走 `registry_census` 单独普查。

### (2) 免费公共 RPC 拿不到完整历史日志，而且有一个会【静默说谎】

| 端点 | 历史区间 `eth_getLogs` |
|---|---|
| publicnode | 报错 `Archive requests require a personal token` |
| drpc 免费档 | 报错 `ranges over 10000 blocks are not supported` |
| **flashbots** | **静默返回 `[]`** |

第三种是本项目最危险的 bug 类：扫描「成功」完成，87% 的区块扫出 0 条日志，
数据被悄悄写坏。已加 `verify_endpoints_for_logs` 金丝雀校验把这类端点剔除。
**但结论不变：完整历史日志必须有 archive 节点。**

### (3) 漏斗主体不需要 archive —— 用当前状态即可

这是最重要的一条，改变了 stage 的优先级。L0→L3 需要的四样东西全是**当前状态**：

| 需要的 | 怎么拿 | 要 archive 吗 |
|---|---|---|
| agent 总数 | `ownerOf(agentId)` 二分（id 从 0 顺序递增），每链约 34 次调用 | 否 |
| 当前 owner | `ownerOf` | 否 |
| agentURI | `tokenURI` | 否 |
| agent wallet | `getAgentWallet` | 否 |

Multicall3 批量读即可（`e8004 snapshot-state`）。**没有 archive key 时，Stage 03
单独就能撑起报告主体。** 历史日志只额外提供：注册时间戳（→ §8.4 队列分析）、
反馈（→ L4）、转让历史（→ 注册 owner vs 当前 owner 对比）。

→ 排期含义：**Stage 03 应提到 T1 之前**。它更便宜、更可靠、且是漏斗的必需品；
日志扫描（T1）降级为「有 archive key 时的增强项」。

### (4) 以太坊主网约有 4.95 万个 agent

从日志里观测到的 agentId 区间 [49407, 49500] 完全连续，且 `max(agent_id)` 说明
主网累计铸造约 49,501 个。这一条也顺带给出一个**领域内的完整性判据**：
agentId 连续，任何缺口都意味着扫漏了日志 —— 比对比第三方计数更早、更便宜。

`e8004 count-agents` 已跑通的链（口径 A，未跨链去重）：
celo 9,765 / gnosis 4,108 / avalanche 1,802 / arbitrum 1,234 / optimism 537 /
mantle 144 / linea 115 / scroll 108。加上以太坊约 4.95 万，已超过 6.7 万；
base / bsc / polygon 因公共 RPC 限流未取到。**「9.8 万」这个量级是站得住的。**

## 0.6 全量实跑后的修正（2026-08-10/11，跑完 39.2 万个身份得到的）

### (1) 规模是 39.2 万，不是 9.8 万

12 条链口径 A 合计 **392,258**。BSC 一条链就占 262,999（67%），且以约 1,800/天增长。
「9.8 万」这个前提本身是错的。各家数字打架（22k/39k/98k/150k）的原因是口径不同 +
BSC 近期爆发。

### (2) 跨链去重几乎不改变数字

口径 B 三档：strong 392,186 / medium 384,135 / weak 382,937。**最宽判据也只压缩 2.4%**。
这 39 万不是「同一批 agent 在多链各注册一遍」。另有 1,016 条【单向】跨链声明被忽略。

### (3) 论文的集中度结论不能外推

在论文同一子集（以太坊 id 0–9999）上，本流水线复现出 Gini **0.863** / HHI **0.034283** /
Top10 **51.40%** —— 与论文六位有效数字全中，且走的是完全独立的路径（当前状态 eth_call
vs 历史日志）。**T8 硬门槛因此不需要 archive 节点也能跑**。

但同样的指标放到全量 39.2 万上是 Gini **0.318** / Top10 **12.65%**，265,921 个不同 owner。
**论文的「高度集中」对它的样本成立，对全量不成立。**

### (4) 所有权分散，端点极度集中 —— 这是最有信息量的一处反差

| 维度 | Gini | 说明 |
|---|---:|---|
| 当前 owner | 0.318 | 26.6 万个不同地址 |
| **端点主机** | **0.935** | 前 2 个 host 覆盖 49% |

注册身份的人很多，真正在跑服务的运营者极少。github.com 覆盖 26% 的 agent（静态文件，
不是服务）。**这个角度论文没做，且比数 owner 更直接地回答「有多少独立主体」。**

### (5) 又一次静默数据损坏 —— 这是本项目第二次

BSC 上一个 agent 把 JSON 片段当 tokenURI（`"animal_kingdom": { ... }`）。`urlparse`
是【惰性】的：它本身不抛错，直到访问 `.port` 才把 ` {   "kingdoms": 1` 拿去转整数。
当时 `try` 只包住 `urlparse()` 没包住属性访问 —— 一个畸形值掀翻了 19.7 万个 URI 的抓取，
而 `run_full.sh` 里的 `|| true` 吞掉了非零退出码，后续三个阶段照常跑完，
**产出一份用 31% 数据算出来、却看起来完整的报告**。

和 flashbots 静默返回空日志是同一个模式。三层都要防：
1. 解析函数对任何畸形输入都必须返回而不是抛（已加 9 个畸形输入的参数化测试，
   立刻又抓出 `normalize_uri` 对畸形 IPv6 同样会抛）
2. 单条记录的异常不许掀翻整轮
3. **覆盖率安全阀**：`funnel` / `report` 自动计算 URI 抓取覆盖率，不足 100% 就标红
   「L1/L1s/L2 不可引用」。编排脚本不许用 `|| true` 吞失败。

### (6) 性能：两处会在 39 万量级卡死的写法

* `parse-cards` 逐行 INSERT → 必须批量 executemany
* `identity_cluster` 用 `INSERT OR REPLACE` 写 39 万行 → DuckDB 逐行做主键冲突检查，
  实测 55 分钟未完；表在前面已 DELETE 清空，冲突不可能发生。改普通 INSERT 后 253 秒。

## 1. 对原始思路稿的事实修正

开工前必须先纠正四处会直接浪费时间的错误认知。以下均已通过 EIP 正文与官方合约仓库核对。

### 1.1 那两组 `0x8004` 地址不是「不同链」，是「主网 / 测试网」

原稿说「检索到两组地址，没法确定哪组对应哪条链」。实际是：官方用确定性部署，**所有 EVM 主网共用同一组地址，所有测试网共用另一组**。

| 环境 | IdentityRegistry | ReputationRegistry |
|---|---|---|
| 主网（Ethereum / Base / BSC / Arbitrum / Optimism / Polygon / Avalanche / Linea / Scroll / Celo / Gnosis / Mantle / Abstract …） | `0x8004A169FB4a3325136EB29fA0ceB6D2e539a432` | `0x8004BAa17C55a88189AE136b182e5fdA19dE9b63` |
| 测试网（Sepolia / Base Sepolia / Amoy …） | `0x8004A818BFB912233c491871b3d84c89A494BD9e` | `0x8004B663056A597Dffe9eCcC1965A193B7388713` |

这对架构有直接好处：**多链扫描退化成一个 `chains.toml` 配置循环**，不需要每条链维护地址映射。

⚠️ 两点仍需在 T0 阶段用代码验证，不要直接信本表：
- ValidationRegistry 的地址**不在 README 表格里**，需要单独发现（见 T0-2）。
- 上表来自对 README 的二次归纳。**必须**用 `eth_getCode` + 调用 `ownerOf(0)` / `getIdentityRegistry()` 实际验证后才能写进配置。

### 1.2 注册事件不是「ERC-721 mint 事件」，有专用事件；且必须同时扫 `Transfer`

原稿说「拉全量注册就是拉 ERC-721 的 mint 事件 + URI 更新事件」。实际规范定义了专用事件：

```solidity
event Registered(uint256 indexed agentId, string agentURI, address indexed owner)
event URIUpdated(uint256 indexed agentId, string newURI, address indexed updatedBy)
event MetadataSet(uint256 indexed agentId, string indexed indexedMetadataKey, string metadataKey, bytes metadataValue)
```

关键推论：**身份是 ERC-721，可以转让**。`Registered.owner` 是注册时的 owner，不是当前 owner。计算所有权集中度时用错会得到不同的数字。所以 `Transfer(address,address,uint256)` 必须一起扫，用于推导 current owner。这也是相对已有论文的一个方法论改进点（见 §2）。

### 1.3 `int128` 之外还有更多坑：indexed string

原稿正确指出了 `int128` + `valueDecimals` 要还原。补充两个同级别的坑：

```solidity
event NewFeedback(uint256 indexed agentId, address indexed clientAddress, uint64 feedbackIndex,
  int128 value, uint8 valueDecimals, string indexed indexedTag1, string tag1, string tag2,
  string endpoint, string feedbackURI, bytes32 feedbackHash)
```

- `indexedTag1` 是 **keccak256 哈希**，不是原文。可读的 tag 在非 indexed 的 `tag1` 里。`MetadataSet.indexedMetadataKey` 同理。解码时必须取非 indexed 字段。
- `NewFeedback` 还带了原稿没提到的 `endpoint` / `feedbackURI` / `feedbackHash`——`feedbackURI` 指向链下评价文件，是 L4 分析的额外证据源，别丢。
- 还有 `FeedbackRevoked` 事件。撤销过的反馈默认应排除，但**撤销率本身是个值得报告的数字**。

### 1.4 agent card 的 `registrations[]` 字段，是解决「9.8 万」口径问题的钥匙

规范定义的注册文件（`type: ".../eip-8004#registration-v1"`）里有：

```json
{
  "registrations": [ { "agentId": 22, "agentRegistry": "eip155:1:0x8004A169..." } ],
  "services": [ { "name": "A2A|MCP|web|OASF|ENS|DID|email", "endpoint": "...", "version": "0.3.0" } ],
  "active": true,
  "x402Support": false,
  "supportedTrust": ["reputation", "crypto-economic", "tee-attestation"]
}
```

- `registrations[]` 是 agent **自我声明的跨链身份列表**。同一个 agent 在 15 条链上各注册一次，链上是 15 条记录，实际是 1 个主体。这个字段让「去重后的唯一 agent 数」变成可计算的，而不是拍脑袋。这直接回答了原稿里「各家统计口径根本不一样」的困惑。
- `active: false` 是 agent **主动声明自己不在服务**。这类必须单独成一支，绝不能和「探测不通」混为一谈——否则就犯了原稿结尾自己警告的那个错误。

## 2. 竞争态势：你的差异化在哪里（这段决定报告价值）

已存在一篇论文：**《From Agent Identity to Agent Economy: Measuring the Operational Readiness of ERC-8004 AI Agents》**（arXiv 2606.12128）。这大概率就是原稿说的「六月那篇论文」。它实际做了什么：

| 维度 | 该论文 | 你的计划 |
|---|---|---|
| 链 | **仅 Ethereum 主网** | 多链（Tier A 深度 + Tier B 普查）|
| 样本 | **前 10,000 个 agent**（id 0–9999），区块 24,339,925–24,839,925 | 全量 |
| agentURI 解析 | **未做**，未报告任何解析成功率 | L1：完整失败分类学 |
| 端点活性探测 | **完全没做**，明确写了「仅基于可观测链上记录与已有元数据」 | L3：四层探测 ×2 轮 |
| 所有权集中度 | 做了：Gini **0.863**，HHI 0.034283，Top10 占 **51.40%** | 复现 + 扩展到 current owner / 多链 |
| 反馈集中度 | 做了：单一最大 client 贡献 **65.82%** 的反馈；client Gini 0.783 | 扩展为自评闭环分层识别 |
| 数据 | 公开（Harvard Dataverse, DOI 10.7910/DVN/HJZW8Q）；代码未公开 | 全开源 |

**结论：原稿说「活性探测是别人没做过的部分」——这个判断成立，而且是唯一成立的。** L3 和 L1 失败分类学是你的护城河，L4 的所有权集中度已经被人做过了。

由此产生两条硬性规划决策：

1. **L3 探测是最高优先级，必须最早跑起来**（它是唯一的原创性来源，且 wall-clock 最长）。
2. **L4 集中度分析改变定位**：从「原创发现」降级为「交叉验证 + 扩展」。这反而是好事——用你的独立流水线在同样的样本（ETH 前 10k）上复现出 Gini≈0.863 / Top10≈51.4%，是**你整条流水线正确性的最强证据**。这条写进验收标准（见 T8 DoD）。

另外，已经有一批第三方索引器/浏览器存在（Agent0 subgraph、RNWY、8004scan.io、Dune `hashed_official/erc8004` 等）。它们的用途是**交叉校验你的 L0 计数**，不是数据源——你的权威数据必须来自自己扫的日志，否则报告不可复现。

顺带一提：各家公开数字彼此矛盾（有说上线前 90 天约 3.9 万注册、有说 12 链 15 万+、有说 16 链 2.2 万+）。**「9.8 万」这个数在开工前应视为未经验证的传闻**，Stage 1 的输出才是答案。

## 3. 技术栈决策

**Python 3.12 + httpx/asyncio + DuckDB + Polars + networkx**，全仓单语言。用 `uv` 管依赖。

理由（原稿说「TS+viem 或 Python+web3.py 都行」，这里必须选一个）：链上扫描在两种语言里都是简单部分，而**第 4、5 步（图分析、Gini、资金溯源、出表）才是价值密集区，Python 在这里是压倒性的**（networkx / polars / scipy）。为了扫描阶段选 TS，会导致 scanner 与 analysis 分裂成两个语言的仓库，对一个两周项目是净损失。

具体选型：

| 用途 | 选择 | 备注 |
|---|---|---|
| JSON-RPC | `httpx` 直接打，自己写 `eth_getLogs` 封装 | **不用 web3.py**。它的 ABI 解码在批量场景偏慢，且我们只需要 4 类事件。用 `eth-abi` + `eth-utils` 做解码即可 |
| ABI 解码 | `eth_abi.abi.decode` + `eth_utils.keccak` | topic0 一律由签名字符串在运行时计算，**禁止硬编码 hash** |
| 存储 | DuckDB 单文件 | 10 万行级别，正确的选择。Parquet 导出用于发布 |
| 数据处理 | Polars | DuckDB 里能用 SQL 做的就用 SQL |
| HTTP 探测 | `httpx.AsyncClient` + 自研双层限速器 | 见 §6 |
| DNS | `aiodns` | |
| MCP 握手 | **手写 JSON-RPC**，不引 MCP SDK | 我们只需要 `initialize`，SDK 会带来重连/会话管理等不需要的行为，且不好控制超时与限速 |
| 图分析 | `networkx` | 规模足够 |
| 大整数 | Python `int` + `decimal.Decimal` | **任何金额/评分禁止用 float** |
| CLI | `typer` | 每个 stage 一个子命令 |
| 报告 | Quarto 或 Jupyter → Markdown + matplotlib | |

## 4. 架构：raw / derived 强制分离

这是整个项目最重要的一条架构规则。

> **只有 Stage 02/04/06/07 可以访问网络。它们只做一件事：把原始响应原封不动落盘。所有解析、判定、统计都是纯函数，只读数据库，可以无限次重跑。**

原因有三：（a）两周内分析逻辑会改二十次，探测只能跑两次——不分离就会反复骚扰别人的服务器，这是原稿划的伦理红线；（b）判定标准（比如「什么算握手成功」）一定会在写报告时改，改了要能重算历史；（c）可复现性——发布的数据集是原始响应，别人能用不同判定标准重算，这才叫科学。

### ⚠️ 落盘缓冲：DuckDB 单写者限制（这条不遵守，T3 第一晚就会撞墙）

**DuckDB 一个文件同时只允许一个进程持有写锁**——写锁存在时，别的进程连只读打开都会失败。这跟 §0 C2 设计的工作方式（长任务夜里挂着跑、你白天开 `duckdb` CLI 翻数据）**直接冲突**。

所以网络 stage **不直接写数据库**：

```
网络 stage  ──写──>  data/spool/<stage>/<run_id>.jsonl   （追加写，不加锁，随便杀）
                              │
                     e8004 load <stage>                   （几秒钟，短暂持锁）
                              │
                              v
                        data/e8004.duckdb
```

三个好处，全都直接对应本项目的约束：

1. 通宵任务不持有数据库锁，你随时能开另一个进程查数据。
2. 抓取/探测进程被杀掉，已完成的部分在 JSONL 里完好无损——**断点续跑的粒度从「整个 stage」降到「单条记录」**。
3. JSONL 是原始响应的第二份备份，入库逻辑改了可以重放，不用重新联网。

`load` 步骤必须幂等（按主键 upsert），且入库后**不删除 JSONL**（它是 raw 层的一部分，要跟着数据集一起发布）。

### 每个 stage 的通用契约

所有 stage 必须满足：

1. **幂等**：重跑不产生重复行（靠主键 + `INSERT OR REPLACE` / `ANTI JOIN`）。
2. **可断点续跑**：进度写 `stage_cursor` 表（`stage, chain_id, cursor, updated_at`）。杀掉进程再启动必须从断点继续。
3. **单一职责**：网络 stage 不做判定，判定 stage 不碰网络。
4. **结构化日志**：`structlog` → JSONL，落 `data/logs/<stage>.jsonl`。

### 快照清单（snapshot manifest）

`snapshot` 表固定每条链的截止区块号 + 区块哈希 + 时间戳。**所有后续查询以此为准**，扫描时不用 `latest`。这让三个月后的复跑可以精确对比，也让报告里每个数字都有可验证的锚点。原稿说「真正的产出是那个可复跑的 scanner」——快照清单就是让它可复跑的那个机制。

## 5. 数据管线分阶段规格

数据库表定义见 [schema.sql](schema.sql)。这里是行为规格。

### Stage 01 —— bootstrap（地址验证 + 部署区块发现）

**输入**：`config/chains.toml` 里的 chain_id + RPC endpoint 列表。

**行为**：
1. 对每条链每个注册表地址执行 `eth_getCode`，非空则存在。
2. 探测性调用验证身份：IdentityRegistry 调 `supportsInterface(0x80ac58cd)`（ERC-721）应返回 true；Reputation/Validation 调 `getIdentityRegistry()`，返回值应等于 IdentityRegistry 地址。**这一步是防止扫错合约的唯一保险**。
3. **部署区块二分查找**：在 `[0, latest]` 上对 `eth_getCode(addr, blockNumber)` 是否为空做二分，约 25 次 RPC 调用定位首个有代码的区块。结果回写 `config/chains.toml` 缓存，后续不再查。
4. ValidationRegistry 地址发现：README 表格里没有。按序尝试 —— (a) 读官方仓库 `abis/` 与 `ignition/modules/` 部署产物；(b) 用区块浏览器搜 `0x8004` 前缀合约；(c) 若确实未部署，在配置里标 `validation_registry = null`，全流程降级跳过。**不要因为找不到它而阻塞主线**。

**输出**：`chain` 表填充完毕；`config/chains.toml` 含 `deploy_block`。

**验收**：见 [开发排期与验收.md](开发排期与验收.md) T0。

### Stage 02 —— logs（全量事件扫描）

**这是权威数据源。** 扫的事件（topic0 运行时由签名计算）：

| 合约 | 事件签名 | 用途 |
|---|---|---|
| Identity | `Registered(uint256,string,address)` | L0 基础 + 注册时 owner |
| Identity | `URIUpdated(uint256,string,address)` | agentURI 最新值 |
| Identity | `MetadataSet(uint256,string,string,bytes)` | agent wallet 等保留 key |
| Identity | `Transfer(address,address,uint256)` | **current owner 推导** |
| Reputation | `NewFeedback(uint256,address,uint64,int128,uint8,string,string,string,string,string,bytes32)` | L4 |
| Reputation | `FeedbackRevoked(uint256,address,uint64)` | 撤销 |
| Reputation | `ResponseAppended(uint256,address,uint64,address,string,bytes32)` | 反馈回应 |
| Validation | `ValidationRequest(address,uint256,string,bytes32)` / `ValidationResponse(address,uint256,bytes32,uint8,string,bytes32,string)` | 可选层 |

**实现要点**：

- **一次 `eth_getLogs` 传地址数组**（`address: [identity, reputation, validation]`），不要每个合约扫一遍。
- **自适应步长**：初始 `range = 10_000`。命中含 `range` / `limit` / `too many` / `-32005` 的错误 → 步长减半重试（最小 1，减到 1 仍失败则真错误，抛出）。连续 5 次成功 → 步长 ×1.5，上限 `max_range`。每条链的收敛步长持久化到配置。
- **重组保护**：扫描上界取 `finalized` 标签（不支持的链退化为 `latest - confirmations`，confirmations 按链配置）。每条日志存 `block_hash`。断点续跑时先校验游标前 N 个区块的 hash 仍匹配，不匹配则回退重扫。
- **解码陷阱**：`string indexed` 参数在 topic 里是 keccak 哈希，**可读值一律从 data 段的非 indexed 同名字段取**。见 §1.3。
- `agent_id` 是 uint256，实践中从 0 递增，存 `UBIGINT`；解码时若超出 `2^63-1` 必须报错而不是静默截断。

**输出**：`log_raw`（原始日志，append-only）+ 各事件解码表。

### Stage 03 —— state（当前状态快照）

在 snapshot 区块高度上，用 **Multicall3**（`0xcA11bde05977b3631167028862bE2a173976CA11`，多链同址）批量读：

- `ownerOf(agentId)` —— 与 Transfer 推导的 current owner 交叉验证，不一致要告警（说明扫漏了日志）
- `getAgentWallet(agentId)` —— **L5 经济活动分析的关键**，原稿把它归到 agent card 里是错的，它在链上可直接读
- `tokenURI(agentId)` —— 与 `URIUpdated` 推导的最新 URI 交叉验证

批大小从 500 起，遇 gas/size 报错减半。

### Stage 04 —— uri_fetch（L1 网络出口 A）

**核心优化：按「规范化 URI」去重，不是按 agent 去重。** 大量 agent 会共享同一个 URI 或同一份内容。先 `SELECT DISTINCT uri`，这个去重系数决定这一步是跑 2 小时还是 20 小时。

按 scheme 分派：

| scheme | 处理 |
|---|---|
| `data:application/json;base64,` / `data:application/json,` | **进程内解析，零网络**。同时支持 base64 与 percent-encoding |
| `https://` / `http://` | GET，超时 10s，最多 3 次重定向，**响应体上限 1 MiB**（防 zip bomb / 巨型文件），记录最终 URL |
| `ipfs://` | 多网关 fallback，见下 |
| `ar://`、`did:`、ENS 名、其他 | 各自单独归类，**不要塞进「失败」桶**——它们是「非常规但未必错」 |

**IPFS 策略（这一步 90% 的时间花在这）**：
- 强烈建议**本地跑一个 Kubo 节点**做首选网关（`http://127.0.0.1:8080`）。9.8 万个 CID 全走公共网关必然被限流打死。
- fallback 链：`local → w3s.link → ipfs.io → dweb.link → cloudflare-ipfs.com`，每个网关独立令牌桶，单次超时 10s，整体最多试 3 个网关。
- CID 提取要同时支持 `ipfs://<cid>` 与 `ipfs://<cid>/path/file.json`。

**失败分类学（这是本 stage 的核心交付物，不是副产品）**：

```
ok | unsupported_scheme | dns_fail | tls_fail | conn_timeout | read_timeout
| http_404 | http_4xx | http_5xx | too_large | not_json | ipfs_unresolvable | other
```

原稿只列了 4 类，这里扩到 13 类。**注意 `not_json` 和 `schema_invalid` 要分开**：前者在本 stage 判定（能不能 parse），后者在 Stage 05 判定（parse 了但不符合规范）。原稿把它们并列在同一层是概念混淆。

**输出**：`uri_fetch`（每个 URI 一行，含状态 + `content_sha256`）+ `data/raw/` 下的内容寻址 blob。

### Stage 05 —— card_parse（L1/L2 判定，纯函数）

读 blob，产出三张表：

- `agent_card`：`schema_valid_strict`（严格符合 registration-v1）、`parsed_lenient`（能解析出 name/services 就算）、`active` 标志、`x402_support`、`supported_trust[]`
- `service`：展开 `services[]` → `(chain_id, agent_id, service_name, endpoint, version)`。**这张表是 Stage 06 的输入**
- `card_registration`：展开 `registrations[]` → 跨链身份声明，Stage 08 去重用

**报告口径**：headline 数字用 `schema_valid_strict`（这才是「符合规范」），下游分析用 `parsed_lenient`（宽容一点才不至于丢样本）。两个数都要出现在报告里。

### Stage 06 —— probe（L3 网络出口 B，项目的核心价值）

四层探测，**每层独立记录**，这样才能报告逐层衰减，而不只是一个终点通过率。

| 层 | 动作 | 记录 |
|---|---|---|
| L3a DNS | A/AAAA 解析 | 解析成功；**特别标记 IP 字面量、localhost、RFC1918 私网地址** —— 「agent 端点指向 127.0.0.1」本身就是一条有新闻价值的发现 |
| L3b TCP/TLS | 建连 + 握手 | 证书过期 / 自签 / 域名不匹配**分别记录，且不算失败**——先做一次校验连接，失败后再做一次不校验连接纯粹用于分类 |
| L3c HTTP | GET 端点 | 状态码、`Server` 头、响应时间、响应体大小 |
| L3d 协议 | 见下 | 协议版本、server name/version、能力清单 |

**协议层细节**：
- **A2A**：GET `<endpoint>/.well-known/agent-card.json`，失败再试旧路径 `/.well-known/agent.json`。判定成功 = 返回 JSON 且含 `name` 且含 `skills` 或 `capabilities`。记录 `protocolVersion`。
- **MCP**：Streamable HTTP —— POST JSON-RPC `initialize`（`Accept: application/json, text/event-stream`），期待 result 含 `serverInfo`。旧服务端 fallback 到 SSE（GET `/sse`）。成功后再发一次 `notifications/initialized` + `tools/list`，然后立即关连接。
  > `tools/list` 是只读且开销极小的一次调用，但能拿到真实能力清单——「声称是 MCP agent 但暴露 0 个 tool」是极有价值的发现。这属于判断调用，**如果你想更保守，删掉 `tools/list` 只留 `initialize` 即可**，代码里用配置开关控制。
- **web**：HTTP 2xx 即通过。

**伦理与工程红线（必须在代码层面强制，不能靠自觉）**：

1. **双层限速**。原稿只说了全局 5 req/s——**这不够**：全局限速允许你把 5 req/s 全砸在同一台主机上。必须加 per-host 限制。
   - 全局：10 req/s（这是「你的总出口礼貌度」）
   - **per-host：1 req / 3s，且同一 host 最多 1 条并发连接**（这才是「对单个服务器的礼貌度」，是真正重要的那个）
2. **并发模型必须按 host 分组**。把目标按 host 分桶，起 N=200 个「host worker」，每个 worker 串行处理自己那个 host 的所有目标。否则 per-host 限速会让全局吞吐塌成个位数。
   - 吞吐估算：约 3 万个唯一 host、每 host 约 4 次请求，全局 10 req/s 是瓶颈 → 一轮约 **3.3 小时**。放夜里跑。
3. **User-Agent**：`ERC8004-Research-Scanner/1.0 (+https://github.com/<you>/<repo>; <你的邮箱>)`。仓库 README 首屏写明这是什么、怎么退出扫描。
4. **只读**。只发 GET / OPTIONS / MCP `initialize` / `tools/list`。禁止 POST 业务接口、禁止任何写操作、禁止认证尝试。
5. **429/503 → 指数退避**，同一 host 累计 3 次即拉黑并跳过其余目标，记为 `rate_limited` 而非失败。
6. **每个端点每轮最多 2 次尝试**，全局禁止重试风暴。
7. `web` 类端点遵守 `robots.txt`。
8. **两轮探测，间隔 ≥48 小时**。产出「两轮都通过（stable-live）」vs「仅一轮通过（flaky）」—— 成本几乎为零，但可信度提升巨大，能挡住「你是不是刚好赶上人家重启」这种质疑。

**输出**：`probe_attempt`（每次尝试一行，含 round 编号）——**原始记录，不做判定**。「是否算活」的判定在 Stage 08 用 SQL 做，随时可改口径重算。

### Stage 07 —— wallet_flow（L5 网络出口 C）

**范围控制**：只对**到达 L2 的 agent**（有 card 且声明了端点）跑这一步。对全部 9.8 万个地址做全量交易史查询会把 API 预算烧穿，而且没有分析价值。

数据源：**Etherscan V2 多链 API**（单 key + `chainid` 参数覆盖多链，比每链一个 key 的老方式省事得多）。免费档约 5 req/s。

两件事：

1. **首笔入金溯源**：`txlist` 按 asc 排序取第一条有 value 的入账 → `first_funder`。每个地址 1 次调用。对 owner 地址 + agent wallet 地址都做。
2. **真实经济活动**：`txlist` + `tokentx`，判定「存在非 gas、非注册交易本身、且对手方不在同一资金簇内的转账」。

**Sybil 聚类**：以 `first_funder` 为边构图 → 连通分量 → 报告最大簇覆盖多少 agent。这是原稿说的「同源 funding 是 Sybil 最硬的信号」的具体算法。

### Stage 07b —— feedback_file（网络出口 D，为下一步产品做市场测量）

**目标**：抓取并解析 `NewFeedback.feedbackURI` 指向的链下反馈文件，测量**有多少反馈真的带支付凭证**。

这一步在纯「写报告」的视角下是可选的，但在 §0 C3 的视角下是最高性价比的一步：它直接测量了你下一个要做的东西（支付凭证 × 声誉绑定）的市场大小。而且**实现成本极低**——完全复用 Stage 04 的抓取器和限速器，只是换个 URI 来源和解析器。

规范定义的反馈文件结构里有这几个关键字段：

```json
{
  "value": 100, "valueDecimals": 0, "tag1": "...", "endpoint": "...",
  "mcp": { "tool": "ToolName" },
  "a2a": { "skills": [], "contextId": "", "taskId": "" },
  "proofOfPayment": { "fromAddress": "0x..", "toAddress": "0x..", "chainId": "1", "txHash": "0x.." }
}
```

**三个可验证的数字**（每一个都是报告里的独立发现）：

1. **`proofOfPayment` 存在率** —— 有多少反馈附了支付凭证。
2. **`proofOfPayment` 链上可核验率** —— 更狠的一层：拿 `txHash` 去链上查，这笔交易真的存在吗？收付方真的匹配吗？**声称付过钱和真的付过钱之间的差额，就是你后续那个产品要解决的问题的定量证明。**
3. **链下 `value` 与链上事件 `value` 是否一致** —— 不一致本身就是数据完整性发现。

**范围控制**：反馈数量级在数万条，且 `feedbackURI` 大量重复/为空。**先 `SELECT DISTINCT feedback_uri WHERE feedback_uri <> ''`**，再决定要不要抽样。链上核验用 `eth_getTransactionByHash`，可批量，便宜。

### Stage 08 —— funnel（纯函数，物化漏斗）

见 §7。全部用 SQL 从上游表算出，**不含任何网络与随机性**，同一份数据库跑两次结果必须逐字节相同。

## 6. 限速器实现要点（`limiter.py`）

单独拎出来讲，因为这是最容易写错、写错后果最严重的一个模块。

```python
class DualLimiter:
    """全局桶 + per-host 桶 + per-host 并发信号量。
    调用方必须 `async with limiter.acquire(host):` 才能发请求。
    两个桶都要拿到令牌才放行；先拿 host 令牌再拿全局令牌，避免持全局令牌空等。
    """
```

- 令牌桶用单调时钟（`time.monotonic()`），不用 `sleep` 累加。
- per-host 桶要有 LRU 上限（3 万个 host 的桶对象常驻内存没问题，但要防无界增长）。
- **host 提取要用注册域（eTLD+1）还是 FQDN？** 用 FQDN，但对同一 IP 的多个 FQDN 追加一层 per-IP 限速（很多 agent 端点是同一台服务器的不同子域，只按 FQDN 限速等于没限）。这一条容易被忽略，但对「大量 agent 由同一主体部署」的场景（本项目预期就是这个场景）至关重要。
- 提供 `--dry-run` 模式：只打印将要请求的 URL 与预计耗时，不发包。全量探测前必须先 dry-run 一次核对量级。

## 7. 漏斗定义（报告骨架）

原稿的 L0–L5 方向对，但定义不够可证伪，且漏了两个必须存在的分支。修订版：

### 分母问题：两套口径并列报告

| 口径 | 定义 |
|---|---|
| **口径 A：链上注册数** | 所有链上 `Registered` 事件去重后的 `(chain_id, agent_id)` 数量。这是「9.8 万」那类数字的可比口径 |
| **口径 B：唯一主体数** | 按 §8 的规则跨链归并后的唯一 agent 数 |

**两个都报，并明确说明差异来源。** 原稿正确指出「第一件有价值的事就是明确定义自己的口径并公开它」——两套并列比选一套更有说服力，因为它直接量化了别人数字打架的原因。

### 漏斗层级

| 层 | 定义（可直接写成 SQL 谓词） |
|---|---|
| **L0** | 链上存在注册记录，且在 snapshot 区块高度未被销毁 |
| **L1** | `agentURI` 成功取回且能解析为 JSON（`uri_fetch.status = 'ok'`） |
| **L1s** | 严格符合 registration-v1 schema（`schema_valid_strict`） |
| **L2** | card 中 `services[]` 非空，且至少一个 endpoint 是可路由的公网地址 |
| **L3a/b/c** | DNS 解析 / TCP+TLS 建连 / HTTP 有响应，逐层记录 |
| **L3** | 协议层握手成功（A2A 拉到 card，或 MCP `initialize` 返回 `serverInfo`，或 web 返回 2xx） |
| **L3-stable** | 两轮探测均达到 L3 |
| **L4** | 收到过至少一条**非自评**、未撤销的反馈（自评定义见 §8） |
| **L5** | agent wallet 或 owner 存在真实经济活动（非 gas、非注册交易、对手方不在同一资金簇） |

### 两个必须单列的旁支

- **「自我声明不活跃」**（card 里 `active: false`）：这类不应计入 L3 失败。它们是**诚实的**，把它们算成「死的」会让报告结论失真。
- **「不可路由端点」**（localhost / 私网 IP / 保留域名）：单独一类。这既不是「活」也不是「服务器挂了」，是「根本没打算对外服务」。

### 表述纪律

报告里**禁止**出现「X% 是假的」「9 成是僵尸」这类表述。原稿这条警告是对的，且要落到代码层面：`report/render.py` 里的模板文案只允许输出「L3 存活率 X%」「其中 Y% 自我声明为不活跃」这类中性描述。注册但无活性的合理原因（开发者试注册、早期占位、未上线项目）必须在报告方法论章节显式列出。

## 8. 关键算法

### 8.1 跨链身份归并（`analysis/dedup.py`）

按置信度从高到低，并查集合并：

1. **强证据**：card 的 `registrations[]` 明确声明了另一条链的 `(agentRegistry, agentId)`，且**对方 card 也反向声明**（双向确认）。
2. **中等**：card 内容 `content_sha256` 完全相同 且 owner 地址相同。
3. **弱**：owner 地址相同 且 card 的 `name` 相同。

报告里给出三档分别的归并结果，让读者自选口径。**不要只给一个数**。

### 8.2 集中度（`analysis/concentration.py`）

Gini、HHI、Top-N 份额。必须**分别**对以下口径各算一遍：

- 注册时 owner vs **当前 owner**（后者才是真实控制权，且是论文没做的）
- 全链合并 vs 单链
- 口径 A（注册数）vs 口径 B（去重主体数）

**流水线正确性验证**：在 Ethereum 主网、agent id 0–9999、区块 24,339,925–24,839,925 这个子集上算注册时 owner 的集中度，结果应接近 Gini **0.863** / Top10 **51.40%**。对不上说明扫描或解码有 bug，必须查清楚再往下走。

### 8.3 自评闭环分层识别（`analysis/graphs.py`）

**分五档记录，不要只给一个布尔值**：

| 档 | 定义 |
|---|---|
| T1 | `clientAddress` == agent 的注册 owner 或当前 owner |
| T2 | `clientAddress` == agent wallet（来自 `getAgentWallet`） |
| T3 | client 与 owner 的 `first_funder` 相同（同源资金） |
| T4 | 反馈交易的 `tx.from` == owner（代付 gas） |
| T5 | 互评环：反馈有向图上长度 ≤3 的环（`networkx.simple_cycles`） |

L4 的「非自评」= 排除 T1–T4（T5 单独报告，因为环状互评的性质更暧昧，不宜直接算作自评）。

### 8.4 注册队列分析（cohort）—— 从单次快照里免费拿到时间序列

**这是决策门（§12）的核心证据，而且一分钱不花。**

单次快照看起来只有一个时间截面，但每个 agent 都带着 `Registered` 事件的 `block_timestamp`。按注册月份分桶，就得到一组队列：

```sql
SELECT date_trunc('month', block_timestamp) AS reg_month,
       count(*) AS registered,
       sum(l1_uri_resolved::INT) AS l1, sum(l3_stable::INT) AS l3_stable
FROM funnel JOIN ev_registered USING (chain_id, agent_id)
GROUP BY 1 ORDER BY 1;
```

为什么这个比总存活率重要得多：

- 总存活率是**存量**指标，被上线初期的一波投机注册永久污染。
- 队列存活率是**增量**指标。「2026-02 注册的 agent 有 3% 活着，2026-07 注册的有 18% 活着」和「一直是 3%」是完全相反的两个结论——前者是生态在成熟，后者是生态在空转。

⚠️ 一个必须承认的偏差：老队列的 agent 有更多时间下线，新队列有存活率偏高的天然倾向（幸存者时间不对称）。**报告里必须写明这一点**，并且用「注册后 30 天内」这种固定窗口做一次对照（对老队列而言这需要历史快照，本次做不了——所以这正是三个月后复跑同一个 scanner 的价值所在，也正是 §11 的论据）。

### 8.5 定点数还原

```python
from decimal import Decimal
real_value = Decimal(value_raw) / (Decimal(10) ** value_decimals)   # value_decimals ∈ [0, 18]
```

`value_raw` 是 **int128，可以为负**。DuckDB 的 `HUGEINT` 正好是 int128，直接存原始值，还原后的十进制值存 `DECIMAL(38,18)`。**任何环节不得出现 float。**

## 11. 资产化设计：让 scanner 长成下一个东西

§0 C3 说真正的交付物是验证器。这一节是把它落到代码边界上——**这些决定必须现在做，否则第二步就是重写而不是扩展。**

### 三步演化路径

| 阶段 | 产出 | 本项目要预留什么 |
|---|---|---|
| 现在（两周） | 一次性快照 + 报告 | —— |
| +1～3 月 | **持续运行的 agent 活性/合规评分器** | 探测库边界、稳定输出 schema、多次快照的时间序列 |
| +3～6 月 | 可被合约消费的评分预言机 / 声誉加权原语 | 评分算法与探测解耦、结果可签名 |

### 现在就要守住的四条代码边界

1. **`e8004.probe` 必须是能独立 `pip install` 的库**，不依赖 DuckDB、不依赖本仓的表结构。输入是一个 endpoint 列表，输出是结构化探测结果。`stages/s06_probe.py` 只是它的一个调用方。这条边界一旦破了，第二阶段就得重写。
2. **输出 schema 版本化**：`{"schema_version": "1.0", "probed_at": ..., "layers": {...}}`。别人（和三个月后的你）会依赖这个格式。
3. **判定与探测彻底解耦**（§4 已强制）。评分算法未来会迭代很多次，探测数据不该跟着重跑。
4. **一切以 `snapshot_id` 为键**。多次快照天然叠成时间序列。这是从「一份报告」变成「一个持续数据集」的唯一机制成本——现在做几乎免费，事后补要重构存储层。

### 复跑成本要压到多低

目标：**一次完整复跑 ≤ 4 小时无人值守 + ≤ 30 分钟人工**。达到这个成本，「每月复跑一次」才是业余时间能长期维持的动作；而连续几个月的时间序列，是别人无法快速追赶的、真正复利的资产（§8.4 里那个「幸存者时间不对称」的偏差，也只有靠历史快照才能消掉）。

把这个当成 T13 的验收标准，不是愿景。

### 现在明确不要做的

不要在这两周里写任何合约、不要建 API 服务、不要做 Web UI。它们都会挤占那几十个小时的注意力预算，而且在数据出来之前，你还不知道该给谁做。

## 12. 决策门：什么数据算「值得继续押一年」

§0 C4：**这些阈值必须在看到数据之前定死。**看到数据再定标准，你一定会自我说服——无论数据是什么样。

### 先破一个陷阱

「L3 存活率很低」这件事**本身不构成 no-go**，因为它有两种截然相反的解释：

- (a) 生态是空的 → 别投入
- (b) 缺口是真的，而且没人补 → 正是你的机会

**区分二者的不是存活率，是绝对量和趋势。** 所以决策看四个信号，不看那个最抢眼的百分比：

| 信号 | 指标 | 来源 |
|---|---|---|
| S1 供给真实性 | **L3-stable 的绝对数量**（不是比率） | Stage 06 两轮 |
| S2 趋势 | 新注册队列的 L3 存活率 vs 老队列 | §8.4 cohort |
| S3 需求真实性 | 收到过**非自评**第三方反馈的 agent 数；带**链上可核验** `proofOfPayment` 的反馈数 | Stage 07 + 07b |
| S4 主体多样性 | 跨链去重后的独立主体数、最大资金簇覆盖率 | §8.1 + Stage 09 |

### 预先承诺的判定规则

| 结论 | 条件 | 行动 |
|---|---|---|
| **GO：做操作层** | S1 ≥ 数百个 且 S2 上升 且 S3 有双位数可核验支付凭证 | 生态在真实成长，按原计划押注 |
| **GO：做验证/评分基础设施** | S1 偏低但在涨、S3 有真实第三方需求信号、S4 显示主体多样 | 缺口是真的且有人需要——你的验证器就是产品，优先级高于任何合约原语 |
| **NO-GO** | S1 是两位数 且 S2 平坦 且 S4 显示独立主体 < 100 | 几个人在自娱自乐。省下一年，报告照发 |
| **观望** | 信号互相矛盾 | 三个月后用同一个 scanner 复跑看 delta |

**最可能落到「观望」。** 这不是决策失败——恰恰相反，它是本项目最重要的论证：一次快照回答不了趋势问题，而你手上会有唯一一个能低成本复跑的工具。**这就是为什么 scanner 比报告值钱**（§11）。

### 无论结论如何，你都保住的东西

即使判定 NO-GO，`e8004.probe` 本质是一个**多链事件扫描 + 服务端点活性探测框架**，和 ERC-8004 的耦合只在 ABI 和 card schema 那一层。任何「注册表 + 链下服务」形态的协议都能复用它。押注可能落空，这部分不会。
