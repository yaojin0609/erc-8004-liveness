# 链上索引的静默数据损坏：八次「看起来成功了」

> 本文记录在 12 条链上扫描 39.2 万个 ERC-8004 注册身份时遇到的八次数据损坏。
> 它们的共同点是**失败时看起来像成功**——不报错、不中断，扫描"完成"并产出
> 一份错的数据集。
>
> 实测时间 2026-08-10 至 2026-08-15。所有结论可用本仓代码复跑核对：
> <https://github.com/yaojin0609/ERC-800>
>
> **关于点名**：下文点出了具体的 RPC 服务商与失败方式。这是**特定时间点的
> 实测记录**，不是对服务质量的评价——公共 RPC 免费额度本就各有取舍，
> 而且可用性会随时间变化（本文中就有一个端点在金丝雀测试时正常、
> 正式扫描时持续 500）。列出来的目的是让后来者能避开，不是指控。

---

## 为什么值得单独写

做链上索引的人通常防的是"报错"：超时、限流、节点挂了。这些好办，
重试和轮转就能解决。

真正危险的是另一类：**上游返回了一个语法正确、结构完整、但内容不全的响应。**
你的代码收到 HTTP 200 和一个合法的 JSON 数组，没有任何理由怀疑它。
扫描跑完，日志显示"✓ 成功"，你拿着这份数据去算指标、写报告、发结论。

八次里有五次属于这一类。剩下三次是"整条链崩溃"——那种至少你知道出事了。

## 第一类：返回了，但内容是错的

### 1. 端点对历史区间静默返回空数组

**`rpc.flashbots.net`**（以太坊主网，2026-08-10 实测）

对部署期的历史区块查 `eth_getLogs`，返回 `[]`。不报错，不说"我不支持归档查询"，
就是一个空数组。

这一条单独出现还不致命，致命的是它和另一个 bug 的组合：当时代码里把扫描步长
写成了 `max_range = max_log_range * 5`，于是步长涨到 5 万，`eth.drpc.org`
报范围错误，客户端轮转到下一个端点——正好是 flashbots——它"成功"返回了 `[]`。

结果：**以太坊 87% 的区间被"成功"扫描，日志数为 0。**

同一天实测的其他以太坊端点：

| 端点 | 历史区间 `eth_getLogs` |
|---|---|
| `rpc.mevblocker.io` | ✓ 正常返回（2,364 条） |
| `ethereum-rpc.publicnode.com` | 403 |
| `eth.drpc.org` | HTTP 400（范围超限） |
| `eth.merkle.io` | HTTP 400 |
| `eth.meowrpc.com` | 500 |
| `1rpc.io/eth` | 明确拒绝 `eth_getLogs` |
| `rpc.flashbots.net` | **静默返回 `[]`** ⚠️（后续测试为 504） |

**怎么发现的**：不是靠日志，是靠数据自身的性质。ERC-8004 的 `agentId` 从 0
顺序递增，扫出来的 id 是 49407–49500 这样连续的一段，但最小值远大于 0——
如果扫描真的覆盖了全区间，最小 id 必须是 0。

**修复**：把步长硬限制回配置值；开扫前做**端点完整性验证**（金丝雀），
拿一个已知含日志的区块去问每个端点，返回空的直接从端点池剔除。
见 [`verify_endpoints_for_logs`](../src/e8004/rpc.py)。

### 2. 返回 HTTP 200 + 截断的结果集

**celo 的公共 RPC**（`celo-rpc.publicnode.com` / `forno.celo.org`，2026-08-13 实测）

这个比返空更阴险：它返回了数据，只是**不全**。

用 50,000 区块的窗口扫描，celo 报告成功，但比链上实际少了 **1,911 个 agent
（该链的 19.6%）**。而**重查同一个区间就能拿到**：

```
区间 [62,232,087, 62,235,907] 重查 → 13 条 Registered
  其中 agentId 3446–3453 全在 —— 正是原扫描漏掉的那批
```

那 8 个 id 连号、同一个 owner，是一次批量铸造。批量铸造会在很窄的区块里堆出
上万条日志，窗口一跨过去就触发截断。

**修复**：celo 的窗口降到 2,000（配置里写死并注明"不要调回 50000"）。
但真正的防线不是调参数——见下文"唯一可靠的防线"。

### 3. 金丝雀校验因覆盖范围不足而被整个跳过

这一条是我自己的 bug，但性质完全一样，而且更值得警惕：**我加的防线被我自己
的另一个改动废掉了，而系统照样报告成功。**

金丝雀校验的实现是"从链头往回找一个含日志的区块"，最多找 12 × 窗口大小。
默认窗口 10,000 时覆盖 12 万个区块。

我把 scroll 的窗口调到 50,000（因为它支持），覆盖范围变成 60 万个区块——
听起来更大了。但 **scroll 的注册活动停在离链头 230 万个区块之前**。
找不到金丝雀 → 校验被跳过（而不是报错）→ 一个静默返空的端点畅通无阻。

结果：`✓ scroll: 0 条日志`。而链上明明有 108 个 agent，`ownerOf(0)`、
`ownerOf(107)` 都能返回持有者。重扫得到 470 条日志。

**讽刺的是：把参数调大反而让防线失效了。**

**修复**：金丝雀在整个待扫区间上均匀取 24 个窗口，从新到旧探（最坏 24 次调用，
相对随后成百上千次的扫描可忽略）。见 [`_find_canary_block`](../src/e8004/stages/s02_logs.py)、
测试 [`test_scan_guard.py`](../tests/test_scan_guard.py)。

### 4. 免费额度把 `eth_getLogs` 砍到 10 个区块

**Alchemy 免费档**（2026-08-12 实测，所有链）

```
Under the Free tier plan, you can make eth_getLogs requests with up to a
10 block range.
```

它**会**报错，所以严格说不算静默。但后果是静默的：客户端把这个错误识别为
"范围过大"，于是折半重试——10,000 → 5,000 → … → 10。然后以 10 个区块的粒度
去爬 139 万个区块。

不报错，不崩溃，只是**永远跑不完**。而且因为它排在端点列表第一位，
只要轮转轮到它，整轮扫描就被拖死。

**修复**：新增 `log_rpcs` 配置项——日志扫描用一份**单独的、实测能拿历史日志
的端点列表**，不让轮转碰运气。Alchemy 绝不能进这个列表。

顺带一提：Alchemy 免费档虽然做不了 `eth_getLogs`，但
`alchemy_getAssetTransfers` 可以一次查全区间并翻页。以太坊的 49,503 条注册
记录用它 50 次请求就拿到了，而走 `eth_getLogs` 需要 139,186 次。
**同一个服务商的两个 API，可行性差 2,700 倍。**

### 5. `|| true` 吞掉失败，让残缺数据跑完整条流水线

一个 BSC 上的 agent 把 JSON 直接塞进了 `tokenURI` 字段：

```
{"animal_kingdom": {"kingdoms": 1, ...}}
```

`urlparse` 对这种输入是**惰性失败**的——解析时不报错，直到你访问 `.port`
才抛异常。而当时的 `try` 只包住了 `urlparse()` 本身。

一个畸形 URI 让整个抓取阶段在 31% 处崩溃。但流水线脚本里那一步写的是
`... || true`，于是**崩溃被吞掉，后续阶段带着 31% 的数据继续跑完，
产出了一份"看起来完整"的报告**。

**修复**：脚本里删掉 `|| true` 并加 `set -o pipefail`，宁可停在那里也不要
产出一份错的。加了 9 个畸形 URI 的参数化回归测试——**这批测试立刻又抓出
第二处同类问题**（`normalize_uri` 对畸形 IPv6 的处理）。

## 第二类：整条链崩溃

这类至少你知道出事了。但它们的成因值得记，因为都属于"错误分类错了"。

### 6. HTTP 400 未归类为范围错误

**celo 的公共 RPC**：窗口内日志太多时，它返回 **HTTP 400**，而不是
JSON-RPC 的范围错误码。

于是折半逻辑（识别到"范围过大"就缩小窗口）**根本不会被触发**。客户端只会
"换个端点重试"，可 celo 两个端点都这样。重试耗尽 → 抛异常 → 整条链崩溃，
9,766 个 agent 的数据全部丢失。

**修复**：`eth_getLogs` 收到 400 时转成范围错误交给上层折半。同时加了反向
测试——**别把所有 400 都当范围问题**，真正的参数错误应该如实报错，
而不是被折半掩盖成死循环。

### 7. 批量调用条数超限未自适应

**`mainnet.base.org`**：每批最多 10 个调用，超了返回 `-32014`。

代码里区块时间戳的批量查询固定 100 条一批，直接崩，base 整条链丢失。

**修复**：按报错文本自适应回退批大小。实测 **100 → 25 → 6**，自己找到上限
后继续跑。

### 8. `DELETE` 破坏索引，一次 Ctrl-C 永久锁死一张表

这个与 RPC 无关，但属于同一类"错误信息指向别处"。

派生表原来用 `DELETE FROM` 清空。DuckDB 的 `DELETE` 要逐行维护主键的 ART
索引，进程在半途被杀会把索引留成不一致状态。下一次 `DELETE`：

```
FATAL Error: Failed to delete all rows from index.
Only deleted 1836 out of 1884 rows.
```

`FATAL` 会让整个连接作废。也就是说——**一次 Ctrl-C 就把这张表永久锁死了**，
之后每次操作都以同样的 FATAL 结束。而报错信息完全指向别处，看着像数据损坏。

**修复**：派生表清空一律 `DROP` 重建，不碰索引内容，且在 39 万行量级上快一个
数量级。加了守卫：raw 层的表永远不许被 DROP（那些数据重新联网才能拿回来）。

## 唯一可靠的防线：用数据自身的性质对账

上面每一条都有针对性的修复，但它们有个共同弱点：**都是在防已知的失败方式。**
第 3 条就是活生生的例子——我加的防线被我自己的另一个改动废掉了。

真正管用的是一条**不依赖上游是否诚实**的检验。这个项目里它是：

> `agentId` 从 0 顺序递增 ⇒ **有注册记录的身份数必须等于普查数。**

普查数走 `eth_call`（`ownerOf` 二分查找），注册记录走 `eth_getLogs`。
**两条完全独立的路径**，一条撒谎另一条会立刻暴露。纯 SQL，不碰网络，
可以随时重跑：

```
$ e8004 verify-coverage
 chain     普查      有注册记录   缺口   结论
 56        262,999   262,999      0      完整
 8453      61,333    61,333       0      完整
 1         49,503    49,503       0      完整
 42220     9,766     9,766        0      完整
 ...
 ✓ 所有链的注册记录数与普查数一致
```

`--strict` 可以挂进流水线当门槛，对不上就退出。

第二道类似的检验是**"0 条日志"必须被证明**：扫完一条链得到 0 条日志时，
用 `ownerOf(0)` 走 `eth_call` 独立反证。链上确实有 token 却一条日志都没有 →
**直接报错**，不许安静地返回一份空数据集。

这类检验的共同特征：

1. **用另一条独立路径验证**，而不是相信同一个来源
2. **利用数据本身的结构性质**（顺序递增、总数守恒、集合包含关系）
3. **纯函数、不碰网络**，可以无限重跑
4. **默认拒绝而不是默认通过**——发现不一致就停，而不是记个警告继续

## 给做链上索引的人的清单

1. **不要相信"扫描成功完成"这个信号。** 找一个独立可算的不变量去对账。
2. **`eth_getLogs` 返回空数组时，先怀疑端点而不是链。** 拿一个已知含日志的
   区块做金丝雀，把静默说谎的端点剔出端点池。
3. **窗口调大是有代价的。** 更大的窗口更容易触发结果集截断（返回 200 但不全），
   而且可能让你基于窗口的校验逻辑失去覆盖范围。
4. **区分"范围过大"和"传输错误"。** 有的端点用 HTTP 400 表达范围问题，
   有的用 JSON-RPC 错误码；归类错了要么崩溃要么死循环。
5. **批量调用的条数上限各家不同且不公布。** 按报错自适应回退，别写死。
6. **能做 `eth_call` 的端点未必能做 `eth_getLogs`。** 为日志扫描单独维护一份
   实测可用的端点列表。
7. **流水线脚本里不要用 `|| true`。** 宁可停在失败处，也不要让残缺数据跑完
   全程并产出"看起来完整"的结果。
8. **公共端点的可用性会变。** 本文里就有一个端点在金丝雀测试时正常、
   正式扫描时持续返 500。端点列表需要定期复核，并且要能容忍单点失效。

## 实测端点清单（2026-08-15）

仅记录"能否拿到部署期历史日志"这一项。**不代表服务质量**，也不保证今天仍然如此。

**以太坊**：`rpc.mevblocker.io` 可用；publicnode 403、drpc/merkle HTTP 400、
meowrpc 500、1rpc 拒绝、flashbots 静默返空（后为 504）。

**Base**：`mainnet.base.org`、`base.gateway.tenderly.co` 可用
（`base.drpc.org` 金丝雀时可用、正式扫描持续 500）；publicnode 403、
meowrpc 500、1rpc 拒绝。tenderly 允许 20 万跨度，但**仍建议用 1 万**——
窗口大了会触发截断。

**BSC**：**只有 `bsc.rpc.blxrbdn.com` 可用**（上限 5,000 跨度）；
publicnode 403、四个 `dataseed` 全部 `-32005 limit exceeded`、
meowrpc 不支持 `eth_getLogs`、1rpc 拒绝、drpc 可用但极易 429、
blockrazor 连 1,000 跨度都超限。

> ⚠️ BSC 这批端点第一次测试时"全部不可用"，是因为我用**并发**同时打了它们，
> 全被限流。串行 + 3 秒间隔才试出 blxrbdn 可用。**测试方式本身会污染测试结果。**

**其余链**（tier B，`eth_getLogs` 最大跨度实测）：celo / avalanche / optimism /
mantle / linea / scroll 均为 50,000，gnosis 为 10,000。
**但 celo 必须降到 2,000**——50,000 的窗口会触发静默截断（见第 2 条）。
