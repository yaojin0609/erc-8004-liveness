好，把它拆成一个真正能执行的两周计划。核心思路是**做一个漏斗**：从「链上注册了」一层层往下筛到「真的在干活」，每一层的存活率就是你报告的骨架。

## 第 0 步：拿到权威数据源（半天）

不要用我给的任何地址直接开工。官方合约仓库在 `github.com/erc-8004/erc-8004-contracts`，三个注册表分别是 IdentityRegistry（基于 ERC-721 的身份）、ReputationRegistry（反馈信号的标准接口）、ValidationRegistry（验证器合约发布结果的钩子），规范正文在 `ERC8004SPEC.md`。

README 里列了各链的部署地址，都用了 `0x8004` 开头的靓号前缀——我检索到的内容里出现了两组（`0x8004A818...`/`0x8004B663...` 和 `0x8004A169...`/`0x8004BAa1...`），但没法确定哪组对应哪条链，你自己去 README 核对。另外注意合约是 `IdentityRegistryUpgradeable.sol` 这类可升级版本——**你要扫的是 proxy 地址，不是 implementation**，这个搞错会一条数据都拿不到。

同时把 EIP 正文（`eips.ethereum.org/EIPS/eip-8004`）通读一遍，它是接口的唯一真相来源。

## 第 1 步：拉全量注册事件（1 天）

规范里 tokenId 叫 agentId，tokenURI 叫 agentURI，用的是 ERC721URIStorage 扩展，注册表是每条链的 singleton。所以拉全量注册其实就是拉这个 ERC-721 的 mint 事件 + URI 更新事件。

三条路，我建议**先 Dune 探路、再自己扫做权威数据**：

- **Dune**：半小时就能出个数量级，用来验证「98k」这个数字到底怎么算出来的。
- **viem / web3.py + archive RPC**（Alchemy 免费额度够）：`eth_getLogs` 按区块分段扫，多数 RPC 对 block range 有限制（常见 2k–10k），写个自动折半重试的循环。这是你真正的数据源。
- Etherscan API 也行，但翻页和限流会让你难受。

跨链是第一个坑：有报道称 BNB Chain 约 3.4 万、Base 约 1.65 万、以太坊主网 1.4 万多，但这几个数加起来跟「9.8 万」和「13 万预测」都对不上。**这说明各家统计口径根本不一样**——有的算累计 mint，有的算当前持有，有的把测试网算进去了。你要做的第一件有价值的事，就是明确定义自己的口径并公开它。

## 第 2 步：解析 agent card（2 天，第一个漏斗层）

agentURI 必须解析到 agent 注册文件，而 URI 可能指向 IPFS，也可能是链上 Base64 内嵌数据。<cite name="80">这个 JSON 里描述的是端点、钱包地址和支持的信任模型。</cite>

工程细节：

- 三种形态分别处理：`ipfs://`、`https://`、`data:application/json;base64,`
- IPFS 用多网关 fallback（ipfs.io / cloudflare-ipfs / dweb.link），单个超时 10 秒
- **失败要分类记录**，别只记成功率：404、超时、JSON 解析失败、schema 不符合规范，这四类的比例本身就是结论

这一步跑完你就有了第一个杀手级数字：**元数据可解析率**。那篇六月的论文说的「元数据可用性有限」，具体到底是 30% 还是 3%，没人公开量化过。

## 第 3 步：活性探测（3–4 天，这是核心）

这是别人没做过的部分，也是你整份报告的价值所在。agent card 里声明的服务端点（A2A 或 MCP），**真的活着吗**？

分层探测，每层记录通过率：

1. 域名能不能 DNS 解析
2. TCP/TLS 能不能连上
3. HTTP 返回什么状态码
4. 协议层握手能不能成——A2A 拉 agent card，MCP 发 `initialize`

**伦理和工程红线，务必守住**：全局限速（5 req/s 这个量级就够，你只有 10 万个目标不赶时间）、User-Agent 里写明这是研究扫描并留联系邮箱、只做只读探测、遇到 429 就退避、失败不要重试风暴。你是在做研究，不是在压测别人的服务。这条守不住，报告发出来会变成负资产。

## 第 4 步：声誉图和所有权图（2 天，最有杀伤力的部分）

ReputationRegistry 里，一条反馈由 clientAddress 给出，内容是带符号的定点数 int128 加上 valueDecimals（uint8，0–18），外加可选的 tag1 和 tag2。注意**别把 int128 当整数直接用**，要按 decimals 还原。

真正要算的是三张图：

- **owner → agent 集中度**：论文提到所有权和反馈活动高度集中。算个基尼系数，看前 10 个 owner 控制了多少身份。
- **反馈图的自环**：clientAddress 和 agent owner 是不是同一个人、或者由同一个地址出的 gas。找出自评闭环的比例。
- **注册钱包的资金溯源**：每个注册钱包的首笔入金来自哪里。同源 funding 是 Sybil 最硬的信号。

这三张图能直接回答「9.8 万个身份里有多少是独立主体」。我猜答案会很难看，但难看才有新闻价值。

|---|---|---|---|
| L0 | 链上注册存在 | ? | 100% |
| L1 | agentURI 可解析 | ? | ? |
| L2 | 声明了服务端点 | ? | ? |
| L3 | 端点协议握手成功 | ? | ? |
| L4 | 有非自评的第三方反馈 | ? | ? |

**技术栈别过度设计**：TypeScript + viem，或者 Python + web3.py，数据落 DuckDB 或 SQLite 就够了，10 万行数据不需要 Postgres。全部代码放一个 repo，开源。

## 两个提醒

**别把「注册了但没活性」直接等同于「假的」。**很多是开发者试注册、是早期占位、是还没上线的项目。你的报告如果下「9 成是假的」这种标题，会被圈内人正确地攻击。诚实的表述是「L3 存活率 X%」，让读者自己判断。

**真正的产出不是结论，是那个可复跑的 scanner。**结论会过期，工具不会。如果三个月后有人想知道这个数字变了没有，他会来跑你的脚本——那时候你就已经在这个位置上了。这比报告本身值钱得多。
