## 先说三个数

**39.2 万，不是 9.8 万。** 截至快照时刻，12 条链上的 ERC-8004 注册身份总数是
**392,258** 个——比常见说法高约 4 倍。仅 BSC 一条链就有 262,999 个，占 67%。
差异的主要来源不是谁算错了，而是口径：是否跨链、是否去重、是否排除销毁。
本文的口径写死在报告里，任何人可以按同一套代码复跑核对。

**21.3% 声明了可路由的服务端点。** 从"链上注册了"到"元数据能取到"再到
"声明了公网可达的端点"，逐层筛下来是 392,258 → 269,527 → 83,649。

**已探测的身份里，47.6% 的服务端点在相隔 48 小时的两次探测中都完成了协议层握手。**
这是本文对"真活着"能给出的最硬的数字。按端点所属主机的规模事后回权到全集，
估计比例是 **38.6%**。

需要立刻说清楚的是：**不要把它读成"只有 3.8% 活着"**。14,900 / 392,258 = 3.8%
这个算法的分母里，包含了 4.1 万个因抽样被排除的身份、5.2 万个未探测的身份，
以及 30 万个压根没声明服务端点的身份。诚实的表述必须分层，每一层的分母都不同。

## 为什么这个 47.6% 比单次扫描的数字可信

### 一、探测了两轮，间隔 48 小时

单次探测分不清"服务稳定运行"和"探测那一刻恰好在线"。所以同一批 51,387 个端点
被独立探测了两次，起跑时间相差 48 小时以上。

| | 通过端点数 |
|---|---:|
| 第 1 轮 | 17,043 |
| 第 2 轮 | 17,006 |
| **两轮均通过** | **16,967** |

关键不是"两轮的总数接近"——两轮各通过 17,000 个但不是同一批，也会得出同样的
总数，那根本不叫稳定。这里是**逐个端点求交集**：第 1 轮通过的端点里，
**99.6%** 在 48 小时后仍然通过。

可达性因此被确认为一个**稳定的二分状态**，而不是时通时不通。这条对整份结论
是决定性的：它意味着这次测量不是某个时刻的偶然采样。

### 二、结果按主机规模做了回权

端点在主机上极度集中：一家 `evoevo.ai` 持有 36,413 个端点。同一主机必须限速到
1 请求/3 秒（见下节"扫描伦理"），不设上限的话全量探测要 182 小时，其中 90% 的
时间在等这一个主机。所以对 14 个最大的主机做了抽样，另外 3,478 个主机全量探测。

抽样让样本偏向小主机。因此最终数字是**按主机分层回权**的：每个主机内部的
抽样是固定种子的随机抽样，其通过率可无偏估计，再按该主机的真实端点数加权。
不回权的话，"1 个端点的小主机"和"3.6 万个端点的大主机"会被按相同权重平均。

回权改变了每一层的数字，且方向不一：TCP 层从 79.2% 降到 64.8%，协议层从
33.2% 升到 38.6%。**不做这一步，报告里每个 L3 数字都是错的。**

### 三、在已发表论文的同一子集上复现了它的结果

作为正确性检验，本流水线在以太坊 agent id 0–9999 这个子集上，独立算出
Gini 0.8630 / HHI 0.034283 / Top10 51.40%——与已发表论文的三项数字**逐位吻合**。

这个检验过程中还发现了一件事：论文将该组数字描述为"注册时 owner"的集中度，
但实测对应的是**当前 owner**。同一子集下注册时 owner 的 Gini 是 0.8753，
HHI 偏差 20.5%。原因是这批身份中 19.2% 已经易主——486 个铸造接收方
收敛成了 394 个当前持有者。这不影响论文的结论方向，但复现时口径要对齐。

## 最反直觉的发现：存活是运营商的属性，不是身份的属性

把每个主机的协议层通过率单独算出来，分布不在中间，而**压在两端**：

| 该主机的通过率 | 主机数 | 覆盖端点数 |
|---|---:|---:|
| 0–10% | 139 | 89,451 |
| 10–90%（8 档合计） | 96 | 8,410 |
| 90–100% | 55 | 60,877 |

**66.9% 的主机落在最两端，覆盖 94.7% 的端点。**中间八档加起来不到 5%。

规模最大的几家几乎全是极值：`evoevo.ai`（36,413 个端点）通过率 100%，
`api.celonova.xyz`（25,455 个）0%，`platform-backend.prod.termix.live`（19,216 个）0%，
`marketplace.olas.network`（5,127 个）97.5%。

**这意味着"某个身份能否握手"几乎不是该身份的独立属性，而是它所在主机的属性。**
同一主机下成千上万个身份的探测结果高度一致，彼此几乎不提供额外信息。

所以"有多少身份活着"这个问题，在数量级上等价于：
**哪些运营商的服务在快照时刻可达，以及各自注册了多少身份。**

把它和所有权数据放在一起看，反差更明显：

| 指标 | 数值 |
|---|---:|
| 不同 owner 地址数 | 265,921 |
| 所有权 Gini（全量，当前 owner） | 0.318 |
| **端点主机 Gini** | **0.9633** |

**注册身份的人很多，真正在跑服务的运营者极少。**已发表论文在以太坊早期
1 万个样本上得到的 Gini 0.863，本流水线能精确复现——但同样的指标在全量上
是 0.318。那个结论不能外推。

这两件事叠加的含义是：**总体存活率对少数几个主机的可达性极其敏感。**
这是一个关于脆弱性的判断，不是关于任何具体身份的评价。

## 关于第三方反馈：这一层还不能当作验证

ReputationRegistry 的历史日志扫出 **486,196** 条 `NewFeedback`，覆盖
**35,654** 个被评价的身份。扫描覆盖以太坊、Base、BSC 三条链的 373,835 个身份，
占全量 **95.3%**。直接的自评几乎不存在——评价者恰好是被评身份当前 owner 的，
只有 **3 / 486,196**。

但有三处让人无法把它当成"被真实使用过"的证据：

**第一，有反馈的身份，服务反而更不容易通。**

| | 端点两轮均通过的比例 |
|---|---:|
| 有第三方反馈的身份（已探测部分，n=5,496） | **39.7%** |
| 全部已探测身份（n=31,332） | **47.6%** |

如果反馈来自真实使用，方向应该反过来。这个差距在只有以太坊数据时是
37.0% vs 47.6%，加入 Base 与 BSC 后仍然成立。

**第二，反馈密度在链之间差了 30 倍，且与身份规模完全脱钩。**

| 链 | 身份数 | 反馈数 | 被评价的身份占比 |
|---|---:|---:|---:|
| Base | 61,333 | 453,474 | **48.3%** |
| 以太坊 | 49,503 | 3,215 | 3.4% |
| BSC | 262,999 | 29,507 | 1.6% |

**Base 持有 16% 的身份，却贡献了 93% 的反馈。**BSC 有全部身份的 67%，
反馈占比不到 7%。如果反馈反映真实使用，很难解释为什么它如此集中于一条链。

**第三，相当比例的反馈来自本身也持有身份的地址**：以太坊 51.1%，Base 37.2%。
这不等于自评（评价对象对不上），但说明反馈主要在生态内部产生，而不是来自外部
使用者。

**结论：本文不把 L4 当作活性的独立证据。**"有多少被第三方验证过"是一个比
"有多少能握手"强得多的主张，现有数据支撑不了它。这一层需要的是反馈内容与
真实调用记录的关联分析，那是下一步的工作。

（其余 9 条链占全量 4.7%，其 ReputationRegistry 日志尚未扫描；那些链上
有多少反馈仍是未知的。另外只有 15.4% 的 L4 身份被探测过，上表第一行
的对比建立在这个子集上。）

## 本文不主张什么

**"探测不通"不等于"无效"或"造假"。**以下情形都会表现为探测不通，而探测本身
区分不了它们：

1. 开发者试注册、测试用途
2. 早期占位，项目尚未上线
3. 服务临时下线或迁移
4. agent card 中声明 `active: false`，即**主动**声明当前不提供服务
5. 端点指向内网/本机地址，本就不面向公网

第 4、5 类在漏斗中**单独成支**，不计入"协议层握手失败"：自我声明不活跃
4,806 个，端点不可路由 1,314 个。

单次快照无法区分"已下线"与"未上线"。要区分它们，需要在不同时间点复跑同一个
扫描器——这正是本项目把扫描器而不是结论作为主要产出的原因。

一个已经能看到的迹象：注册时间越早的身份，元数据可解析率越低
（2026-01 注册的 37.6%，2026-05 注册的 86.0%）。但这既可能是衰减，
也可能是早期队列本身质量不同。**单次快照给不出因果，本文不下这个结论。**

## 扫描伦理

所有出站请求携带如下 User-Agent，指向本仓库与联系邮箱：

```
ERC8004-Research-Scanner/1.0 (+https://github.com/yaojin0609/ERC-800; <联系邮箱>)
```

代码层面强制的约束：

- 全局 ≤10 请求/秒；**单一主机 ≤1 请求/3 秒，且最多 1 条并发连接**；另有 per-IP 限速
- **只读**：仅 GET / OPTIONS / MCP `initialize` / `tools/list`。无任何写操作、认证尝试、
  或向业务接口 POST
- 遇 429/503 退避并将该主机移出本轮；每个端点每轮最多 2 次尝试
- 每次请求前检查退出名单（`config/blocklist.txt`），即时生效

**不希望被扫描**：发邮件到上述地址，或直接提 PR 加入退出名单。

第一轮探测中有 1,988 个端点触发了限速器的三振退出（记为 `rate_limited`
而非"失败"，不计入不活跃）；第二轮同样节奏下只有 60 个。这说明第一轮那批
大概率是那些主机当时自身的状态，而不是扫描节奏的问题。

## 方法与可复现性

整个流水线只有 4 个阶段接触网络，且只负责把原始响应落盘；所有判定与统计都是
纯函数，可以无限重跑而不再打扰任何人的服务器。口径改了能立刻重算历史，
而不需要重新扫描。

**扫描过程中遇到并修复了五次"静默数据损坏"**——RPC 端点不报错、返回不完整
的数据，扫描"成功"完成并产出一份错的数据集：

| 表现 | 真相 |
|---|---|
| 以太坊扫描正常完成 | 某端点对历史区间返回空数组，87% 的数据是空的 |
| scroll「成功扫描 0 条日志」 | 端点完整性校验被跳过，静默返空的端点通过 |
| celo 少 19.6% | 端点返回 HTTP 200 + **截断的**结果集 |
| celo 整条链崩溃 | HTTP 400 未归类为范围错误，折半逻辑不触发 |
| base 整条链崩溃 | 批量调用条数超限，未自适应回退 |

**共同点是扫描自己发现不了。**因此加了一道不依赖 RPC 是否诚实的对账：
`agentId` 从 0 顺序递增，所以有注册记录的身份数必须等于普查数。纯 SQL，
不碰网络，作为流水线门槛。当前状态：**12 条链全部一致，缺口为 0。**

这份数据集的每一个数字都可以用同一套代码复跑核对。三个月后用同一个扫描器
再跑一次，就能把"衰减"和"从未上线"分开——那才是这个项目真正的产出。
